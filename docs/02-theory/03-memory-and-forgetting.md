# 记忆与遗忘

> 一个什么都记得的角色，会长成一个什么都无所谓的人。

## 为什么不能全记住

直觉上，长期陪伴的 AI 应该把所有聊天记录都记住。实际做下来，这是最快的毁掉角色的方法。

三个原因：

**一、噪声会淹没信号。** 三个月有几万条对话，其中绝大多数是"嗯""在吗""吃了"。真正的信息（她怕虫子、外婆住院了、她讨厌被问复习到哪了）夹在中间，占比不到百分之一。检索时它们跟噪声平权，结果就是每次召回一堆废话。

**二、没有遗忘就没有轻重。** 人会忘记昨天中午吃什么，但记得三年前的一句话。这个差别本身就是意义。什么都记得的人，什么都一样重。

**三、上下文放不下。** 这个是最实际的。别说几万条，几千条就到上限了。

所以第一件要做的不是"怎么记住更多"，是**"怎么忘得有道理"**。

## 记忆分几层

做了四层，各层走不同规则：

| 层 | 内容 | 半衰期 |
|---|---|---|
| 日常 | 今天发生了什么、说了什么 | 30 天 |
| 项目/技术 | 做了什么、为什么这么做 | 100 天 |
| 关于人的 | 这个人什么样、我们之间发生过什么 | 200 天 |
| 锚点 | 角色的核心设定、长期约定 | 不衰减 |

半衰期不是一个魔数，是观察出来的：

- 日常给 30 天，是因为两周前的一句闲聊如果还想得起来，那它一定被反复提过（见下面"回忆强化"）
- 关于人的给 200 天，是因为"他怕虫子"这种事，一年后还该记得
- 锚点不衰减，是因为它不叫记忆，叫身份

**踩过的坑**：一开始统一给 50 天。结果是三个月后，角色的日常全忘了，"关于他"的部分也模糊了——因为最该留下的是人，结果跟流水账一起衰减了。

## 三个强度因子

单纯的半衰期还是不够。同样是"今天发生的事"，有些该留，有些该走。

所以每条记忆算三个数：

**S（意义强度）**：这条内容本身多重。出现关系人名、被否定、自述（"我怕……""我不喜欢……"）加权重；如果里面全是技术词，乘以 0.4 降权——技术细节不属于"她的人和事"。

**I（身份相关性）**：这条跟"她是谁"有多近。自述、她的世界锚点（园子、外婆、那条街）、别人怎么叫她，都算高。这一格的用途是让"关于她的"记忆比"关于工作的"活得更久。

**E（情绪残留）**：这条当时带着多强的情绪。开心、难过、被戳到，都留一点余温。

然后寿命这么算：

```
半衰期 = 基础天数 × 加权 / ((1 - E) × (1 - C))

加权 = min(1.8, (1 + 0.6S)(1 + 0.8I)(1 + 0.35 × min(2, 强度)))
```

三个因子都在放大寿命，但乘起来封顶 1.8 倍。

**为什么封顶**：第一版没封顶，乘出来能到 3 倍。3 倍的时候，20 天前的日常条目新鲜度还有 0.89——等于不忘了。封到 1.8 之后，流水账还是 50 天走完，她自己的日常能撑到 94 天，吃满加成的 31 条全是角色设定。

这个上限是调出来的，不是算出来的。调的依据是"哪些条目永远不该消失"——答案只有设定，所以上限要刚好让设定吃满、别的吃不满。

## 回忆会反向强化

一条记忆被想起来一次，就该活得更久一点。

```
寿命倍率 = 0.5 / (1 + 0.5 × 次数)
```

次数越多，倍率越小——**边际效用递减**。想起第一次加很多，想起第十次几乎不加了。这是对的：一条被反复想起的记忆早该固化了，不需要每次再加一遍。

**一个换算的坑**：老数据的"次数"是累加计数，不是从 0 开始的新条目。直接套公式，那些历史次数很高的条目永远长不大。得先做一次底数换算：

```
新底 = 0.22 × ln(1 + 老次数)
```

没做这个换算之前，有一条出现了 44 次的记忆，寿命还是最短的那档。

## 去重：同一天说的同一句话

同类内容的重复很普遍——"吃了吗"连说三遍、"要交作业"连说六条。这些如果都进库，检索时会被同一个意思占满名额。

做法：**同一个来源（同一天、同一份文档）里，两两算相似度，超过阈值就连成一簇，只留最长的一条。**

阈值定在 0.90（裸点积，因为向量已经归一化）。

**这个数是怎么定的**：不是找分布断点找出来的。实测那天的数据里，0.90 以上有 34 对，几乎全是真重复；0.85~0.90 有 166 对，其中七成真、三成只是格式像。所以取严不取宽。

**跨天不合并**：今天说"累"和上周说"累"是两件事，代表两个不同的日子。合并了就丢掉时间。

结果：一次重建里 3136 条标出 233 条副本（7%），实际可检索 2903 条。

## 幻觉治理：这一层比检索更重要

检索做得再好，模型也会编。而且它编得很有说服力——因为它在模仿"回忆"的语气。

三条硬规矩：

**一、检索不到就是检索不到，不要拿相近的顶替。**

最初的设计里，如果向量没对上，会按"这个人"兜底翻旧账——这看起来是贴心，实际是冒充命中。她会让模型说"你上次也这样"，而"上次"根本不存在。

改法：加一个哨兵值。真检索到就返回内容，没检索到就返回一个特殊标记，提示词里明确写"（这句你翻过记忆了，没有这条记录。）"

**二、弱命中要用"存疑"，不要用"记不太清"。**

"记不太清"会变成一个圆谎的模板——下一句就能顺理成章地编。而"存疑"是个技术标记，它不提供编的入口。

**三、分不开的时候承认分不开。**

实测数据：真命中的最高分 0.794，误命中的最高分 0.840。**误命中比真命中分还高。**

所以靠调阈值解决不了"沾边但答非所问"。这时候只能在提示词层面加一句："想不起来的事别编，真记不得就问回去。"

## 时间问句走日期，不走向量

"今天怎么样""昨天说过什么"这类问题，走向量检索是死路——因为向量比的是语义相似，不是时间。"今天"和"上周三"在语义上几乎没区别。

做法：先判断问句里有没有时间词（今天、昨天、前天、刚才、上周、这周、最近、以前），有的话直接按日期倒读，不走向量。

**这一条解决了一整类问题**：之前问"今天"，她会翻出一堆老账，因为那些条目的语义更"典型"。

**顺带一个坑**：不能用"最近被访问时间"当"内容时间"。被检索过的旧条目会全变成今天，问"今天"就翻出一堆老账。得从正文或来源路径里取真实日期。

## 两本账不能掺在一起

这是做完之后才发现的更大问题。

记忆库里实际上混着两种东西：

- **她的人和事**：谁说了什么、她当时什么感觉、园子里出了什么事
- **项目的技术流水**：改了什么代码、为什么这么改、踩了什么坑

前者是她的记忆，后者是工程日志。

混在一个索引里的后果：技术条目字数长、词频高，向量检索时天然压过"他怕虫子"这种短而真的句子。她越来越像一个技术文档检索器。

现在的办法是靠来源白名单过滤。长远看应该拆成两个库——但这不是检索层能修的，问题在写入端。

**这可能是这类系统最常见的设计错误：以为"记忆"是一个东西，其实至少是两个。**

## 一条经验

不要把"记住多少"当指标。指标是：

**问一句关于她的人和事，她能不能答上来，而且答对。**

记忆系统做得好的时候，这个数字会自己安静地涨。做不好的时候，加多少条都没用。
