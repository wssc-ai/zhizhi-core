# 运维与踩坑

> 这套系统最难的部分不是让它说得好，是让它连着跑三个月不出事。

## 一、长跑系统会以什么方式坏

先说结论：**它不会"崩"，它会"安静地错"。**

三个月里出过的事，按严重程度排：

| 现象 | 真正的原因 | 发现花了多久 |
|---|---|---|
| 索引一星期没更新，新记忆全搜不到 | 定时任务根本没挂上去 | 一周 |
| 感情分记了三个月，一直等于默认值 | 查表的键名用错（用了会话 ID，表里存的是用户 ID） | 三周 |
| 她一直"有点累"（醒了 31 小时） | 睡眠判断条件是"隔 6 小时没心跳"，而心跳只隔几秒 | 一周 |
| 检索质量一直很差 | 向量没归一化，相似度全被拉到 1.0 | 一天（但影响了一周的数据） |
| 她突然开始抖四行心里话 | 一个函数定义了但从来没被调用 | 半天 |
| 兜底通道配了等于没配 | 剔除不可用选项之后，候选列表空了 | 半天 |

**共同点：全部不报错。**

所以在这个系统里，最重要的工程能力不是写代码，是**建一套能在安静出错时报警的检查**。

## 二、一个体检脚本

写了一个 42 项的体检，每天跑一次。它查的都是"应该对但可能悄悄错了"的东西：

- 索引多少条、几小时前更新的、向量模长是不是 1.0
- 三个端口在不在听、进程是什么时候起的
- 心情/身体/信任文件多少天没更新
- 备份目录存在吗、最新的那份是哪天
- 星图多久没重算
- 今天日记写了吗、多大
- 检索自检：固定几个问题，看有没有命中

**关键设计：它不是"测试"，是"体检"。**

测试是"通过/失败"，体检是"这项看着不对劲"。比如"索引 6 小时没更新"不是失败——可能只是因为今天没写东西。但它值得被列出来看一眼。

现在的输出：`通过 42 项，失败 0 项，留意 0 项`。

**"留意"这一档很重要**：把"可能有问题的"和"确实坏了的"分开，才不会因为一堆噪音把这个脚本关掉。

## 三、进程怎么活下来

这是 Windows 上最麻烦的一段。

**第一层：守护进程。**

一个 Python 脚本，每 30 秒检查一次核心端口，不通就拉起来。同时管着日任务（凌晨备份、建索引、体检、回归测试）。

**第二层：看护的看护。**

守护进程本身死过一次——整整一夜没跑。查 Windows 事件日志，**没有任何崩溃记录**。没有崩溃记录意味着不是崩的，是被杀的（signal 杀进程不留痕）。

最大的嫌疑是自己：那天晚上我在重启核心，顺手把守护也带走了。

修法三条：

1. 守护启动时写一个 pid 文件（至少下次能看出是几点起的）
2. 加一个"让一让"开关：手动重启核心之前写一个标记文件，守护看到五分钟内有这个标记就先不拉
3. 再加一层定时任务，每 10 分钟检查守护在不在，不在就拉起来

**重启核心的固定流程**（后来写进了操作纪律）：

```
1. 写标记文件 .core_restarting
2. 停旧进程
3. 等 4 秒
4. 起新进程
5. 等 22 秒
6. 查新端口 owner 和启动时间
7. 删标记文件
```

**为什么必须这么走**：不写标记的话，守护会在你停掉核心的 30 秒内把它拉起来，然后你手动起的那个就成了孤儿进程，占着端口起不来。

## 四、Windows 上的两个大坑

### 坑一：进程完整性等级

这个坑花了一整天，症状极其误导。

现象：某个子进程启动即失败，报 `EPERM: operation not permitted`，指向一个配置文件。

根因：**在某些目录下的进程会被打上"低完整性"标签**，然后它就没有权限写用户目录下的东西。

诊断路径很长：

1. 看日志，报 EPERM
2. 查文件权限，一切正常
3. 手动用同一个命令跑，成功
4. 那就不是权限的事，是进程本身被降权了
5. 查进程的完整性标签，果然是 Low
6. 查为什么是 Low：因为父进程在某个带标签的目录里

**修法**：对那些需要写的目录，把低完整性标签的写权限加上（`icacls <dir> /grant "*S-1-16-4096:(OI)(CI)(M)"`）。

**教训**：Windows 上"文件权限正常但写不进去"，去查进程的完整性等级。

### 坑二：脚本文件的编码

用编辑器存的无 BOM UTF-8 脚本，PowerShell 5.1 会按 GBK 读。

后果不是报错，是**中文注释变成乱码**，而乱码进了一个要传给系统 API 的命令行字符串，导致 API 一直返回"参数无效"。

同一个命令手敲就成功，从文件里跑就失败。

**修法**：`.ps1` 文件必须带 BOM 存。

## 五、备份：四层，缺一层就不算能恢复

只备份"数据"是不够的——真出事那天，你不知道该装哪些东西。

现在的四层：

**第一层：痕迹**

角色的所有产出：日记、想明白的事、走神、事实、岔路口、世界状态、目标、她排的日子、对话记录、人物画像。

这一层是**只有一份、丢了就没了**的东西。

**第二层：代码**

所有源文件。

**第三层：环境**

装了什么、什么版本：

- 依赖清单（`pip freeze` 的完整输出，202 个包）
- 模型清单（本地跑了哪些模型）
- 一份"从零恢复"的步骤文档，九节
- 密钥文件（单独放）

**第四层：运行时本体**

这一层最容易被忽略，但它才是"能不能恢复"的关键：

- 那个几十 GB 的模型权重
- 运行时本体（几百 MB 到几 GB）
- node 之类的二进制

**为什么必须拷**：这些东西都可以重新下载，但下载可能需要几小时，而且**有些版本下不到了**。

### 踩过的坑：静默失败

第一版备份脚本，遇到复制失败是 `except: continue`——跳过，继续。

结果：那个 7 GB 的模型权重没拷进去（U 盘是 FAT32，单文件上限 4 GB），**日志照样打印"完成"**。

发现方式是手工核对文件数，对不上。

三条教训：

1. **备份脚本必须断言。** 写完要检查：源有多少文件、目标有多少、总字节数对不对
2. **磁盘格式先验。** FAT32 单文件上限 4 GB，exFAT 没有
3. **失败要算失败。** `except: pass` 在备份脚本里是犯罪

### 另一个坑：短路的粒度

备份脚本有"今天备过就跳过"的逻辑（`.done` 文件）。

问题是：**本地备份和 U 盘备份共用了这个短路。** 同一天重跑时，本地那层跳过了，U 盘那层也跳过了。

结果：U 盘上只有第四层，前三层根本没进去。

后来的处理：**取消短路**。复制几十个小文件是秒级的事，不值得省这点时间。`.done` 只当"备到几点"的记录。

## 六、索引会自己腐化

记忆索引是这套系统里最大的一个文件（几十 MB），也是最容易出问题的地方。

**腐化方式一：定时任务没挂上。**

有一次索引停在一周前——期间所有新记忆都不在索引里，检索自然搜不到。

原因：**根本没有任何定时任务在跑建索引**。只有衰减任务在跑。

**腐化方式二：增量更新用错了判断依据。**

建索引时，为了省时间，会复用上次算好的向量。

判断"能不能复用"的写法是：`如果上一条有向量，就复用`。

问题：条目是会移动的。往文档中间插一条，后面所有条目的序号都往后挪一位——然后新文本套上了旧向量。

**实测**：同一段文本，现场重算的向量和存储的向量余弦相似度只有 0.41。

修法：判断依据从"有没有上一条的向量"改成"文本的哈希是不是一样"。

```python
same_text = hash_of(prev.text) == hash_of(current.text)
vec = prev.vec if (same_text and prev.vec) else None
```

**腐化方式三：多进程抢写。**

两个进程都会写这个文件（一个负责建索引，一个负责记访问次数）。

做法是"写临时文件 + 原子改名"，所以文件永远不会写坏。但**最后写的那个赢**——另一次写的内容丢了。

现在的判断：可以接受。丢的只是访问计数，影响衰减和排序，不影响内容。真要修得把访问统计拆到单独的文件里，是一摊独立的活。

## 七、死代码

有个函数写好了，改也改了，但**从来没被调用**。

表现：它该做的事一直没做（四行心里话被当台词发出去）。

所以写了个工具扫"定义了但没调用"的函数。18 个可疑项里，真正死的有 3 个。

**判断死代码不能只看名字**：因为这套东西有大量"通过字符串动态调用"和"跨模块 import"，静态扫会误报。所以这个工具输出的是"可疑清单"，要人看一遍。

## 八、日志纪律

长跑系统的日志，唯一的用途是**出事之后能还原现场**。

几条做法：

**一、每个阶段都记。** 过闸的每个"不回"都要记理由。不记的话，她不说话了，你查不出来是漏水还是她不想说。

**二、记原始输出，不只记长度。** 早期只记"拿到 12 字"和"回 0 条"，出事时完全看不出模型到底写了什么。后来加了一行：`原文: '...'`（截断 160 字）。

**三、时间戳用本地时间，不用 UTC。** 排查时对不上号。

**四、日志要有中文。** 不是为了好看——排查的时候你得能一眼看出这是在干什么。

## 九、一条总结

这套系统里，**做过的事有一半是在修"安静地错"**。

所以如果有人要抄这套东西，最有价值的不是那些设计，是这几条：

1. 每个"应该一直在跑"的东西，配一个"它还在跑吗"的检查
2. 每个"应该有值"的状态，配一个"它还是这个值吗"的检查
3. 备份要断言，不要相信日志上的"完成"
4. 所有"跳过"都要有理由，所有"失败"都要留痕
5. 改了处理函数，grep 一遍确认它在调用链上
