# 整体架构

> 四块积木，一个进程，一条消息从进来出去要三十秒。

## 切法

系统被切成四块，切法是按"变更频率"来的——改变最快的东西放最外面。

```
┌─────────────────────────────────────────────┐
│  运维层（守护 / 看板 / 备份）                 │  每天可能改
├─────────────────────────────────────────────┤
│  核心（收消息 → 过闸 → 拼 prompt → 调模型 →   │  每周可能改
│       分句 → 发送 → 写日记）                  │
├─────────────────────────────────────────────┤
│  状态层（心情、身体、身体、信任、日程、目标）  │  每月可能改
├─────────────────────────────────────────────┤
│  记忆库（建索引 / 检索 / 衰减 / 去重）        │  很少改
└─────────────────────────────────────────────┘
```

**为什么不合成一个。** 因为记忆库要能被"只读工具"独立跑（体检、星图、去重），核心要能被重启而不影响索引，状态层要能在不改核心的情况下单独调参。混在一起，改一处要重启全部。

**一个具体的分工细节**：核心和状态层是两个独立的进程组。核心重启时，记忆库在跑它的定时任务，状态文件是纯 JSON 存在磁盘上——谁都不会因为对方重启而丢东西。

## 一条消息的旅行

从收到一条 QQ 消息到发出回复，大概是这样：

**1. 进管道（几毫秒）**

消息进一个七阶段的管道。每阶段可以改 `ctx`，也可以 `skip` 掉整轮（记下为什么）。七个阶段是：解析 → 过闸（回不回）→ 想（调模型）→ 回（分句、发送）→ 记账。

**2. 过闸（10~30 毫秒）**

这一层决定"这轮回不回"。不是简单判断"是不是 @ 我"，而是十来个条件叠在一起：

- 群聊还是私聊
- 是不是被点名
- 忙不忙（手上在干什么）
- 心情如何（概率带）
- 是不是黑名单号
- 有没有理由不回（1/40 概率的"就是没说"）

**这一层的设计原则**：所有"不回"都必须有日志理由。不然哪天她不说话了，查不出来为什么。

**3. 拼 prompt（50~200 毫秒）**

这是整个系统里最重的一块，也是最能决定"像不像人"的一块。见下一节。

**4. 调模型（1~30 秒）**

主通道是云端大模型。挂掉时走本地兜底——但兜底只保"别说错"，不保"说得好"。

**5. 分句（几毫秒）**

模型一次输出的是整段话，要切成几条消息。这一块的规则见 [人设与说话](02-persona-and-speech.md)。

**6. 发送（每条间隔 1~2 秒）**

故意慢。秒回三条不像人，像客服机器人。

## prompt 是怎么拼的

这是核心的一块，也是最容易做错的地方。

**分层的，不是一大段。**

```
## 你是谁
（角色卡 + 说话方式，固定）

## 现在跟你说话的这个人
（他的画像、你们的信任分、上次聊到哪）

## 你现在
（时间、身体、心情、手头在干什么）

## 这段时间（背景，不是你此刻正在做的事）
（世界观、别人这几天在过什么、前面等着的事）

## 记忆
（检索到的相关条目，可能没有）

## 规则
（不该做的事，很短）
```

**为什么中间要加那条括号说明。**

之前出过一个很怪的现象：她前一句说"蹲在台阶上吃夜宵"，下一句说"在拿豆腐"。查了半天，原因是世界观那一大段（几千字）被放在"你现在"段里，模型分不清哪些是"此刻正在发生"、哪些是"世界的背景"。

**问题不是长度，是时空坍缩。** 加一个明确的分段标题，把它标成"背景"，就好了。不用删内容。

**一个更隐蔽的坑。**

有个变量返回的是元组 `(做什么, 心情)`，拼接时直接用了 f-string：

```python
today += f"你{doing}。"     # doing 是 tuple
```

结果 prompt 里出现的是 `你('蹲在台阶上吃夜宵', '饿坏了')。`

模型就照着这个读，然后回答得很怪。

这类 bug 的特征是：**不报错，只是效果变差**。要不是某天把 prompt 打出来看了一眼，永远发现不了。

**所以：prompt 必须能被完整打印出来看。** 我们专门写了一个工具，只干一件事——把某次对话的 prompt 拼好打印，不调模型。

## 时间都花在哪

实测一条消息（有上下文、有记忆检索）：

| 阶段 | 耗时 |
|---|---|
| 过闸 | ~20 ms |
| 拼 prompt（含记忆检索） | ~150 ms |
| 调模型 | 1.5~3 s |
| 分句 + 发送 | 2~4 s（多条消息的间隔） |

**模型占九成。** 所以所有优化都该往模型那边走：减少上下文、合并请求、换更快的通道。

但有个反例：看图。本地视觉模型单张 9~40 秒，加上它整轮要 30 秒以上。这时候的优化方向就不是"更快"，是**"别让它堵住消息"**——超时就先回话，图晚点再说。

**这条判据很实用**：如果一个环节的耗时超过了人的耐心（大概 5 秒），那不要优化它，要**异步化**它。

## 状态存在哪

全是 JSON / JSONL，明文，人可以直接读。

```
data/
  mood.json         心情（PAD 三轴 + 强度）
  body.json         身体（醒多久、累不累、季节）
  trust.json        信任分（每个人一条）
  people.json       人的画像和备注
  dayplan/          日程
  self/plan/        她自己排的日子
  intent/           她自己起的目标
```

**为什么不用数据库。**

三个理由：

1. 这些文件小（最大几十 KB），而且是**整体读写**——没有查询需求
2. 出了问题，用记事本就能看、能改、能修
3. 备份就是复制文件，不需要导出

代价是要自己处理并发写。做法统一是「写临时文件 + 改名」，原子替换，多进程同时写也不会写坏（代价是可能丢一次写，但不会损坏）。

## 一个反直觉的设计

**核心不知道"她现在心情怎么样"。**

它只知道 `mood.style()` 返回的 `{max_lines: 1, meme_p: 0.1}`。

她心情差这件事，不会以任何形式出现在提示词里。只有参数变了。

这个设计的目的是前面说的那条：**凡是写进提示词的内部状态，都会变成表演。** 所以宁可她"不知道自己心情差"，只要她表现出来的样子是心情差。

代价是调试变难了——出了问题不能问"你为什么这样回"，只能去看参数。但换来的是不演。
